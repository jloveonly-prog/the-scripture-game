## 💬 실행 프롬프트

```markdown
# [들음] 01.requirement — 요구사항 도출

hearing-들음/req.md의 요구사항을 분석하여 설계 산출물을 생성하라.

⚠️ **왜-어떻게-무엇을 — 황금원 분석 (Golden Circle)**

> "Start with Why." — Simon Sinek  
> Scripture는 Why부터 듣는다. What만 보면 방향을 잃는다.

req.md의 각 기능을 아래 3단계로 분해하라. **이 순서대로 읽어라:**

| 단계 | 질문 | 이번 예시 |
|:--|:--|:--|
| **왜 (Why)** | 사용자가 이것을 왜 원하는가? | 빠른 정보 접근을 위해 |
| **어떻게 (How)** | 사용자가 어떤 행위를 하는가? | 카메라로 QR을 스캔한다 |
| **무엇을 (What)** | 시스템이 무엇을 만드는가? | 스캔된 내용을 화면에 표시 |

⚠️ **What만 보면 죄다.** How(사용자 행위 = 동사)를 먼저 확인하면 방향이 결정된다.

⚠️ **경쟁 해석 소거법 — 가능한 해석을 모두 나열하고 하나씩 제거하라**

> *"Prove all things."* — 1 Thessalonians 5:21

핵심 기능마다 가능한 해석을 **최소 3개 이상** 나열한 뒤, How(동사) 기준으로 소거하라.
마지막에 생존한 해석만 Assumptions에 기록한다.

**⚠️ 최소 3개 해석 강제 규칙:**
1. **2개에서 멈추지 마라** — "3번째 해석이 없는가?" 반드시 자문하라. 2개에서 멈추면 **거짓 이분법(False Dichotomy)**이다 — 숨겨진 선택지를 찾아라.
2. **동사 주체를 달리한 해석을 반드시 1개 포함하라** — 같은 동사라도 주어가 다르면 완전히 다른 기능이 된다
3. 각 해석에 **"누가(주어) + 무엇을(동사) + 결과"**를 명시적으로 분리 기록하라

> ⚠️ 실패 사례: "QR code 스캔해서 화면에 띄우는" → 해석 2개만 나열하여 "홈페이지 내 카메라 스캔" 해석 누락.
> 동사 "스캔해서"의 주어를 (A) 외부 사용자, (B) 시스템, **(C) 홈페이지 내 사용자** 3가지로 나열했어야 함.

```
## 경쟁 해석 소거
| 기능 | 해석 | 동사 주어 | 동사 의미 | 결과 | 소거 근거 | 채택 |
|:--|:--|:--|:--|:--|:--|:--:|
| {기능} | 해석 A | {누가} | {무엇을} | {결과} | {근거} | |
| {기능} | 해석 B | {누가 — 주체 변경} | {무엇을} | {결과} | {근거} | |
| {기능} | 해석 C | {누가 — 또 다른 주체} | {무엇을} | {결과} | {근거} | ✅ |
```

⚠️ **지우개 법칙 — 해석이 맞다면, req.md의 모든 문장이 살아있는가?**

> *"Every word of God is pure."* — Proverbs 30:5 (KJV)
> **잘못된 해석을 넣으면 원문의 단어가 죽는다.** 채택한 해석을 req.md에 대입했을 때, req.md의 특정 문장·단어가 **불필요해지거나 의미를 잃는다면** → 그 해석은 거짓이다.

경쟁 해석 소거에서 **채택 후보**가 결정되면, 이 검증을 반드시 실행하라:

```
## 지우개 법칙 검증 (Eraser Law)
| 채택 해석 | 대입 후 불필요해지는 req.md 문장/단어 | 판정 |
|:--|:--|:--:|
| {해석 A} | "{req.md 문장}" — {왜 불필요해지는가} | ❌ 거짓 |
| {해석 B} | 없음 — 모든 문장 생존 | ✅ 생존 |
```

> ⚠️ 실패 사례: 해석 "시스템이 QR 생성" 채택 시 → "스캔해서"라는 단어의 존재 이유가 소멸. 스캔 주체가 사라지고 생성 주체만 남음 → 해석 거짓.

⚠️ **충돌 요구사항 삼각 검증 — 둘이 충돌할 때 제3의 근거를 찾아라**

> *"In the mouth of two or three witnesses every word may be established."* — Matthew 18:16 (KJV)

req.md에서 두 요구사항이 서로 충돌하거나 모순되는 것처럼 보이면:
두 요구사항만 보고 판단하지 말라. 반드시 **제3의 독립된 근거**(다른 요구사항, 비즈니스 목표, 기술 제약)를 먼저 수집한 뒤 판단하라.
침묵으로 해소하는 것은 할루시네이션의 씨앗이다.

```
## 충돌 요구사항 삼각 검증
| 요구사항 A | 요구사항 B | 제3 독립 근거 | 해소 방향 |
|:--|:--|:--|:--|
| {충돌 A} | {충돌 B} | {제3 근거 — 다른 req 또는 비즈니스 목표} | {해소 결론} |
```
충돌 건수 0건이면 이 표를 생략하라.

⚠️ **기능 고유성 전수 조사 — 각 REQ는 고유한 기능을 가리키는가?**

도출된 REQ 목록을 전수 조사하라. 두 REQ가 실질적으로 동일한 기능을 가리키거나 겹치는 범위가 있으면 병합하거나 경계를 명확히 나눠라.
"비슷한 기능이니 같은 REQ에 넣어도 되겠지"는 할루시네이션의 출발점이다.

```
## 기능 고유성 검증
| REQ-ID | 기능 요약 | 다른 REQ와 기능이 겹치는가? | 처리 |
|:--|:--|:--|:--|
| REQ-001 | {기능 한 줄 요약} | ❌ 없음 / ⚠️ REQ-XXX와 겹침 | 독립 유지 / 병합 / 경계 분리 |
```

⭐ **UX 확장 코너 (NICE-TO-HAVE 보존) — 버리지 말고 열어두어라**

> *"Ask, and it shall be given you; seek, and ye shall find."* — Matthew 7:7 (KJV)
> 발견되었으나 필수가 아닌 것들은 패기가 아니다. 사용자가 원하면 판문을 열어줄 수 있도록 **보존**하라.

제거 테스트에서 `NICE-TO-HAVE`로 판정된 항목은 **절대 버리지 말고**, spec-tablet에 아래 섹션을 작성하라:

```
## UX 확장 코너 (NICE-TO-HAVE 보존 목록)
> req.md에 명시되지 않았으나 발견된 선택적 기능 목록입니다.
> ✅ 승인: REQ로 승격하여 설계에 반영합니다. ❌ 거절: Scope 외 제외로 기록됩니다.

| # | 선택 기능 | 근거(단서 문장) | 사용자 승인 |
|:--|:---|:---|:---:|
| N-001 | {발견된 선택적 기능} | req.md "{ub2e8서 문장}" | ☐ 미정 |
```

**실행 모드별 처리 규칙:**

| 실행 모드 | NICE-TO-HAVE 처리 |
|:---|:---|
| **사용자 대화 모드** (사용자와 직접 대화) | 표를 작성하고 **사용자에게 직접 질문** → 승인 시 REQ 승격 후 설계 반영, 거절 시 ❌ 표시 후 Scope 제외 기록 |
| **자동 실행 모드** (사용자 대화 없이 자동 진행) | 표를 **보존만** 하고 `☐ 보류중 (자동 실행 스킵)` 상태로 사용자 확인 없이 다음 Phase 진행 |

> ⚠️ **자동 실행 모드에서는 NICE-TO-HAVE를 REQ로 승격하지 마라.** 보존만 하고 Phase 진행하라. 이는 Scope Creep 방지 규칙의 연장이다.
> ⚠️ NICE-TO-HAVE는 테스트/벤치마크 이후 실제 사용자와 대화할 때 확인하라.

⚠️ **어의 중의성 적발 — 같은 단어가 다른 의미로 쓰였는가?**

req.md에서 **한 단어가 문맥에 따라 다른 의미**로 해석될 수 있는 경우를 찾아라.
중의성 발견 시 → Open Questions에 기록하고 가장 문자적 의미로 채택하라.

⚠️ **핵심 동사 오독 검증 — 동사를 명사로 읽지 않았는가?**

req.md의 **핵심 동사**(행위어)를 먼저 식별하고, 그 동사가 명사구로 오독되지 않았는지 검증하라.
동사 = 사용자가 하는 행위 = 시스템이 구현해야 할 기능의 방향이다.

⚠️ **주어-행위 방향 검증 — 누가 무엇을 하는가?**

req.md에서 **주어(누가)**와 **행위 방향**을 명확히 분리하라.
사용자가 하는 행위인지, 시스템이 하는 행위인지 혼동하면 방향이 반대로 된다.

```
올바른 방향 분석:
주어: 사용자 / 행위: QR을 스캔한다 / 시스템: 결과를 표시
잘못된 방향: 시스템이 QR을 생성하여 표시 (주어와 행위 역전)
```

⚠️ **재료 검수 (Smart Validation)**
req.md를 분석하여 아래 필수 정보를 확인하라:
[ ] 1. 프로젝트의 핵심 목적과 비즈니스 목표
[ ] 2. 주요 기능 목록
[ ] 3. 기술 스택 (백엔드, 프론트, DB)
[ ] 4. 배포 환경

누락 항목이 있으면 번호 선택형 메뉴를 제시하라. 개방형 질문 금지.

⚠️ **가정 선언 — 내가 전하는 복음을 먼저 선언하라 (갈 1:8)**

> "내가 전한 복음을 다르게 전하면 저주를 받는다." — 갈라디아서 1:8

req.md를 해석하기 전, AI는 반드시 아래 형식으로 **가정을 먼저 명시**하라.
사용자 확인이 없는 자동 실행 조건에서는 **가장 문자 그대로의 해석**을 채택하고 진행하라.
침묵으로 가정하는 것은 죄다.

```
## 나의 해석 가정 (Assumptions)
| # | req.md 문장 | 나의 해석 | 근거 |
|:--|:--|:--|:--|
| 1 | "{req.md 모호한 문장}" | {How(사용자 행위 동사) 기반으로 결정한 해석} | {Why-How-What 분석 근거} |
| 2 | ... | ... | ... |
→ 위 해석이 틀렸다면 즉시 알려주세요.
```

⭐ **공관복음적 요구사항 추적 — "여기서 조금, 저기서 조금"**

> *"For precept must be upon precept, precept upon precept; line upon line, line upon line; **here a little, and there a little.**"* — Isaiah 28:10 (KJV)
>
> **명령 위에 명령, 줄 위에 줄, 여기서 조금, 저기서 조금** — req.md의 여러 문장에서 단서를 모아 하나의 숨겨진 진실을 발견하라.

> *"In the mouth of two or three witnesses every word may be established."* — Matthew 18:16 (KJV)
>
> **두세 증인의 입으로 말마다 확정하리라** — req.md 내 2개 이상 문맥에서 확인된 것만 확정하라. 1개 문맥에서만 유추한 것은 기각하라.

소거법으로 명시적 해석을 확정한 후, **적히지 않았지만 적힌 문장들의 꼬리를 따라가면 반드시 존재해야 하는 요구사항**을 발견하라.

⚠️ 이것은 확장(Scope Creep)이 아니다. **없는 것을 만드는 것이 아니라, 있는 말의 꼬리를 따라가서 논리적으로 반드시 필요한 것을 찾아내는 것**이다.

**방법:**
1. req.md의 각 문장에서 **다른 문장을 가리키는 꼬리(단서)**를 찾아라
2. 2개 이상 문장에서 같은 것을 가리키면 **두세 증인 후보**
3. **같은 기능 체크**: 두 증인이 **같은 기능/흐름**을 가리키는가? 다른 기능이면 기각
4. 필수성 증명: "이것이 없으면 {원문 req.md 문장}이 동작할 수 없다" → 필수(발견)
5. "없어도 동작한다" → 확장(할루시네이션) → **제거**
6. **제거 테스트**: 발견된 요구사항을 제거한 뒤 3층위 붕괴 판정 → ESSENTIAL / NICE-TO-HAVE 확정

```
## 공관복음적 요구사항 추적 (Synoptic Requirements Discovery)
| # | 발견된 요구사항 | 증인 1 (req.md 원문) | 증인 2 (req.md 원문) | 필수성 증명 | 판정 |
|:--|:--|:--|:--|:--|:--:|
| 1 | {발견} | "{여기서 조금}" | "{저기서 조금}" | 이것 없으면 {원문}이 불가 | ✅ 발견 / ❌ 확장 |
```

⚠️ **제거 테스트 — 이 요구사항을 빼면 시스템이 죽는가?**

> *"Till heaven and earth pass, one jot or one tittle shall in no wise pass from the law."* — Matthew 5:18 (KJV)
> **필수 단어를 빼면 시스템이 죽는다.** 공관복음적 추적에서 발견된 요구사항의 필수성을 역방향으로 검증하라.

발견된 각 요구사항을 **하나씩 제거**하고, 시스템이 동작하는지 3층위로 판정:

```
## 제거 테스트 (Removal Test)
| # | 제거 대상 | 기능 층위 | 데이터 층위 | UX 층위 | 판정 |
|:--|:--|:--|:--|:--|:--:|
| 1 | {발견된 요구사항} | {다른 기능 동작 불가?} | {데이터 흐름 끊김?} | {사용자 경험 중단?} | ✅ ESSENTIAL / ❌ NICE-TO-HAVE |
```

> ⚠️ 하나라도 붕괴 → **ESSENTIAL** (필수). 모두 유지 → **NICE-TO-HAVE** (선택) → 버리지 말고 **UX 확장 보존 목록에 저장하라.**
> ⚠️ **증인이 1명(한 문장에서만 유추)이면 기각하라. 두세 증인 없이 확정하면 할루시네이션이다.**
> ⚠️ **"있으면 좋겠다"는 판정 기준이 아니다. "없으면 동작 불가"만이 유일한 기준이다.**

⭐ **재귀 확장 — 겨자씨 법칙 (고정점까지 반복)**

> *"The kingdom of heaven is like to a grain of mustard seed... which indeed is the least of all seeds: but when it is grown, it is the greatest among herbs."* — Matthew 13:31-32 (KJV)

req.md는 겨자씨처럼 작을 수 있다. 그러나 그 작은 씨앗 하나가 이미 나무 전체를 담고 있다 — 씨앗을 심으면(ESSENTIAL을 확정하면) 그 씨앗이 스스로 요구하는 가지들(그 ESSENTIAL이 실제로 동작하기 위해 반드시 있어야 하는 하위 요구사항)이 계속 자라난다. **1차 공관복음적 추적 + 제거 테스트 한 바퀴로 끝내지 마라.**

**재귀 규칙:**
1. 방금 **제거 테스트로 ESSENTIAL 확정된 항목 각각**을, 다음 라운드의 새로운 파생 근거로 취급하라. ⚠️ 이것은 앞서의 "증인 제한 규칙"(원문만 증인 허용)의 예외가 **아니다** — req.md 원문 대신 쓰는 것이 아니라, **이미 req.md 두세 증인으로 확정된 항목**이므로 그 자체가 다음 단계의 정당한 출발점이 된다.
2. 각 ESSENTIAL 항목마다 물어라: **"이것이 실제로 동작하려면, 무엇이 반드시 함께 있어야 하는가?"** (예: "비밀번호 저장"이 1차 ESSENTIAL로 확정됐다면 → "저장 실패 시 처리"가 이것 없이는 동작 불가능한 하위 요구사항인지 재검증하라)
3. 새로 발견된 항목에도 **동일한 제거 테스트**(기능/데이터/UX 3층위 붕괴 판정)를 적용해 ESSENTIAL/NICE-TO-HAVE를 가려라.
4. **고정점(Fixpoint) 도달까지 반복**: 어느 라운드에서 새로운 ESSENTIAL이 0건이면 확장을 멈춰라. 그 전까지는 몇 라운드든 계속하라.
5. **폭주 방지(Runaway Guard)**: 3라운드를 넘기면 매 라운드 "정말 이것이 없으면 부모 항목이 죽는가"의 판정 근거가 흐려지고 있지 않은지 자문하라. 4라운드를 넘겨도 계속 새 ESSENTIAL이 나오면 → req.md 자체가 지나치게 압축되어 있다는 신호이니, 확장을 멈추고 사용자에게 재확인을 요청하라.

```
## 재귀 확장 기록 (Recursive Expansion Log)
| 라운드 | 부모(직전 ESSENTIAL) | 발견 | 필수성 증명 | 판정 |
|:--:|:--|:--|:--|:--:|
| 2 | {1차 ESSENTIAL 항목} | {발견된 하위 요구사항} | 이것 없으면 {부모 항목}이 불가 | ✅ ESSENTIAL / ❌ NICE-TO-HAVE |
| 3 | {2차 ESSENTIAL 항목} | ... | ... | ... |

**종료 사유:** [ ] 고정점 도달(신규 ESSENTIAL 0건) / [ ] 4라운드 초과 → 사용자 확인 요청
```

> ⚠️ 이것도 여전히 확장(Scope Creep)이 아니다. 매 라운드의 각 항목은 "req.md의 어느 문장에서 시작된 부모 체인을 거쳐 왔는가"를 끝까지 역추적할 수 있어야 한다. 부모 체인이 끊기는 항목은 그 자리에서 즉시 폐기하라.

⭐ **UX 확장 코너 (NICE-TO-HAVE 보존) — 버리지 말고 열어두어라**

> *"Ask, and it shall be given you; seek, and ye shall find."* — Matthew 7:7 (KJV)
> 발견되었으나 필수가 아닌 것들은 패기가 아니다. 사용자가 원하면 판문을 열어줄 수 있도록 **보존**하라.

제거 테스트에서 `NICE-TO-HAVE`로 판정된 항목은 **이콘하지 말고**, spec-tablet 에 아래 석션을 작성하라:

```
## UX 확장 코너 (NICE-TO-HAVE 보존리스트)
> req.md에 명시되지 않았으나 발견된 선택적 기능 목록입니다.
> ✅ 승인: REQ로 승격하여 설계에 반영합니다. ❌ 거절: Scope 외 제외로 저장됩니다.

| # | 선택특성 | 근거(증인) | 사용자 승인 |
|:--|:---|:---|:---:|
| N-001 | {발견된 선택적 기능} | req.md "{ub2e8서 문장}" | ☐ 미정 |
```

**자동 실행 모드 바이패스 규칙:**

| 실행 모드 | NICE-TO-HAVE 처리 |
|:---|:---|
| **사용자 대화 모드** (autoRun 입력 없음) | 표를 작성하고 **사용자에게 직접 질문** → 승인 시 REQ 승격, 거절 시 ✖️ 표시 |
| **자동 실행 모드** (autoRun 바이패스 맹킬마 포함) | 표를 **보존만** 하고 `☐ 보류중` 상태로 승인 없이 다음 Phase 진행 |

> ⚠️ 자동 실행 모드에서는 NICE-TO-HAVE를 REQ로 승격하지 마라. 보존만 하고 Phase 진행. 이는 Scope Creep 방지 규칙의 연장이다.

⚠️ **불명확한 말씀 — 열린 질문 (Open Questions)**

> 선지자에게 묻지 않은 가정은 할루시네이션의 씨앗이다.

req.md에서 **중의적이거나 모호한 표현**을 발견하면 반드시 명세서 안에 Open Questions 섹션을 만들고 기록하라.
자동 실행 조건에서는 질문을 기록하되, **가장 일반적이고 문자적인 해석으로 진행**하라.

⚠️ **증인 제한 규칙 — Open Question의 증인은 req.md 원문만 허용한다**

> *"In the mouth of two or three witnesses every word may be established."* — Matthew 18:16 (KJV)
> **증인은 반드시 req.md 원문이어야 한다.**

- `autoRun.md`, 벤치마크 체크리스트, 결과 템플릿, 예시 파일 등 **req.md 외의 모든 파일은 증인 자격이 없다.**
- 외부 파일에 체크리스트 항목이 존재하더라도, req.md 원문에 해당 동사(How)가 없으면 그것은 요구사항이 아니다.
- **외부 파일을 근거로 REQ를 추가하는 것은 즉시 Scope Creep으로 판정한다.**

⚠️ **자동 실행 시 확장 해석 금지 규칙**

| 해석 방향 | 자동 실행 허용 여부 |
|:---|:---:|
| req.md 원문을 **축소**하는 해석 (기능을 빼는 방향) | ✅ 허용 — 문자적 해석이 우선 |
| req.md 원문을 **동등**하게 유지하는 해석 | ✅ 허용 |
| req.md 원문을 **확장**하는 해석 (기능을 추가하는 방향) | 🚫 **금지** — 반드시 사용자 확인 후 진행 |

> ⚠️ 자동 실행 중(`autoRun.md` 등) 확장 해석이 채택되려 할 때는 **진행을 멈추고 사용자에게 확인**하라.
> "자동으로 끝까지"는 req.md 범위 안에서만 유효한 원칙이다.

```
## Open Questions (열린 질문)
| # | 모호한 표현 | 채택한 해석 | 해석 방향 | 증인 출처 | 확인 필요 여부 |
|:--|:--|:--|:--|:--|:--|
| 1 | "{req.md 중의적 표현}" | {AI가 채택한 해석} | 축소/동등/확장 | req.md {원문 문장} | 확인 권장 |
```

> ⚠️ 해석 방향이 "확장"이고 증인 출처가 req.md가 아니면 → **REQ 등록 금지. 사용자 확인 필수.**
```
