## 3. 유스케이스 상세

### UC-001: 게스트 닉네임으로 입장한다

| 항목 | 내용 |
|:---|:---|
| UC-ID | UC-001 |
| 유스케이스명 | 게스트 닉네임으로 입장한다 |
| 행위자 | ACT-001 (플레이어) |
| 연결 REQ | REQ-002, FR-012, FR-078, NFR-003, NFR-008 |
| 전제 조건 | 플레이어가 브라우저로 게임 주소에 접속함. 서버(Worker)가 실행 중 |
| 사후 조건 | 브라우저에 닉네임·게스트 ID·게스트 토큰이 저장되고, 서버에 프로필(레이팅 1000)이 생성되며, 로비 화면이 표시됨 |

**정상 경로 (Main Path — 좁은 길):**
1. 시스템이 브라우저 저장소를 확인하고, 저장된 게스트 정보가 없으면 닉네임 입장 화면을 표시한다
2. 플레이어가 닉네임을 입력하고 입장 버튼을 누른다
3. 시스템(클라이언트)이 닉네임 길이·허용 문자를 1차 검사한다
4. 서버가 닉네임을 검증하고 중복이 아님을 확인한 뒤, 게스트 ID·게스트 토큰을 발급하고 프로필(레이팅 1000)을 저장한다
5. 시스템이 닉네임·게스트 ID·토큰을 브라우저에 저장한다
6. 시스템이 로비 화면(모드 선택)을 표시한다

**대안 경로 (Alternate Path — 다른 길):**
- 1a. 브라우저에 게스트 정보가 이미 있으면 → 서버가 토큰을 검증하고 닉네임 입력 없이 로비 화면을 표시한다

**예외 경로 (Exception Path — 넓은 길):**
- E1. 닉네임이 비었거나 길이·문자 규칙 위반 → "닉네임 규칙(길이·문자)을 확인하세요" 메시지, 입력 화면 유지
- E2. 서버가 중복 닉네임으로 거부 → "이미 사용 중인 닉네임입니다" 메시지, 입력 화면 유지
- E3. 저장된 토큰이 서버 검증에 실패(위조·만료) → 브라우저 게스트 정보를 지우고 닉네임 입장 화면 표시
- E4. 서버 연결 실패 → "서버에 연결할 수 없습니다. 잠시 후 다시 시도하세요" 메시지와 재시도 버튼

### UC-002: 모드와 위인을 고른다

| 항목 | 내용 |
|:---|:---|
| UC-ID | UC-002 |
| 유스케이스명 | 모드와 위인을 고른다 |
| 행위자 | ACT-001 (플레이어) |
| 연결 REQ | REQ-003, REQ-004, REQ-005, REQ-006, FR-013, FR-078, C-008, C-010 |
| 전제 조건 | UC-001 완료 (로비 화면) |
| 사후 조건 | 선택한 모드와 위인으로 다음 단계(매칭 대기·초대 코드·봇 대전·연습)가 시작됨 |

**정상 경로:**
1. 시스템이 로비에서 모드 4가지(대전-랜덤 매칭 / 대전-친구 초대 코드 / AI 봇 대전 / 연습)와 전적·랭킹·옵션 메뉴를 표시한다
2. 플레이어가 모드를 고른다 (AI 봇 대전이면 쉬움·보통·어려움 중 하나를 함께 고른다)
3. 시스템이 캐릭터 선택 화면에 다윗·솔로몬·베드로·바울 4명을 벡터 엠블럼, 스킬 이름·효과, KJV 근거 구절과 함께 표시한다
4. 플레이어가 위인 1명을 고르고 확정한다
5. 시스템이 모드에 따라 UC-003(랜덤 매칭) / UC-004(초대 코드) / UC-005(봇 대전) / UC-006(연습)으로 진행한다

**대안 경로:**
- 4a. 플레이어가 뒤로 가기를 누르면 → 로비 화면으로 돌아가 모드를 다시 고른다

**예외 경로:**
- E1. 위인을 고르지 않고 확정 → 확정 버튼 비활성 상태 유지, "위인을 선택하세요" 안내
- E2. 콘텐츠(heroes.json) 로드 실패 → "게임 데이터를 불러오지 못했습니다" 메시지와 새로고침 안내

### UC-003: 랜덤 매칭으로 대전을 시작한다

| 항목 | 내용 |
|:---|:---|
| UC-ID | UC-003 |
| 유스케이스명 | 랜덤 매칭으로 대전을 시작한다 |
| 행위자 | ACT-001 (플레이어), ACT-005 (Matchmaker) |
| 연결 REQ | REQ-004, REQ-001, FR-018, FR-020, FR-005, FR-008, C-006 |
| 전제 조건 | UC-002에서 "대전-랜덤 매칭" + 위인 선택 완료 |
| 사후 조건 | 두 플레이어가 같은 GameRoom에 연결되고 같은 시드로 첫 라운드가 시작됨 |

**정상 경로:**
1. 클라이언트가 WebSocket(partysocket)으로 서버에 `join`(토큰, heroId)을 보낸다
2. Matchmaker가 플레이어를 대기열에 넣고, 시스템이 매칭 대기 화면("상대를 찾는 중", 취소 버튼)을 표시한다
3. Matchmaker가 대기열에서 레이팅(Elo) 차이가 가장 작은 상대를 찾아 두 사람을 짝짓고 GameRoom을 배정한다
4. 서버가 두 플레이어에게 `matched`(roomId, 상대 닉네임·heroId)를 보낸다
5. 두 클라이언트가 `ready`를 보낸다
6. GameRoom이 두 플레이어에게 `start`(seed, countdown)를 보내고, 시스템이 카운트다운 효과음과 함께 대전 화면(내 보드 + 상대 보드)을 표시한다
7. UC-007로 라운드가 진행된다

**대안 경로:**
- 3a. 대기열에 다른 플레이어가 1명뿐이면 → 레이팅 차이와 관계없이 그 플레이어와 짝짓는다
- 2a. 플레이어가 취소 버튼을 누르면 → Matchmaker가 대기열에서 제거하고 시스템이 로비로 돌아간다 (FR-020)

**예외 경로:**
- E1. 대기 중 연결이 끊김 → Matchmaker가 대기열에서 즉시 제거(유령 매칭 방지), 클라이언트는 재연결 후 로비 표시
- E2. `matched` 후 상대가 `ready` 전에 연결이 끊김 → GameRoom이 남은 플레이어에게 "상대가 나갔습니다" 알림 후 매칭 대기로 되돌림
- E3. 토큰 검증 실패 → "입장 정보가 올바르지 않습니다" 메시지 후 UC-001로 이동

### UC-004: 친구 초대 코드로 대전한다

| 항목 | 내용 |
|:---|:---|
| UC-ID | UC-004 |
| 유스케이스명 | 친구 초대 코드로 대전한다 |
| 행위자 | ACT-001 (방장 플레이어), ACT-002 (초대받은 플레이어), ACT-005 (Matchmaker) |
| 연결 REQ | REQ-004, REQ-001, FR-019, FR-005, FR-008 |
| 전제 조건 | 두 플레이어 모두 UC-001 완료. 방장은 UC-002에서 "대전-친구 초대 코드" + 위인 선택 |
| 사후 조건 | 두 플레이어가 같은 GameRoom에서 같은 시드로 대전을 시작함 |

**정상 경로:**
1. 방장이 "방 만들기"를 누른다
2. 서버가 GameRoom을 만들고 초대 코드를 발급하며, 시스템이 코드와 "친구를 기다리는 중" 화면을 표시한다
3. 방장이 코드를 친구에게 직접 전달한다 (게임 밖 수단)
4. 친구가 로비에서 "코드로 입장"을 고르고 위인을 선택한 뒤 코드를 입력한다
5. 클라이언트가 `join`(토큰, heroId, roomCode)을 보내고, 서버가 코드를 확인해 같은 GameRoom에 연결한다
6. 서버가 양측에 `matched`를 보내고, 양측 `ready` 후 `start`(seed, countdown)로 대전이 시작된다

**대안 경로:**
- 2a. 방장이 대기 중 취소하면 → GameRoom을 닫고 코드를 무효화한 뒤 로비로 돌아간다

**예외 경로:**
- E1. 존재하지 않거나 만료된 코드 → "초대 코드를 찾을 수 없습니다" 메시지, 입력 화면 유지
- E2. 이미 두 명이 들어간 방의 코드 → "이미 가득 찬 방입니다" 메시지
- E3. 방장이 대기 중 연결이 끊김 → GameRoom을 닫고 코드를 무효화 (이후 친구 입장 시 E1)

### UC-005: AI 봇과 대전한다

| 항목 | 내용 |
|:---|:---|
| UC-ID | UC-005 |
| 유스케이스명 | AI 봇과 대전한다 |
| 행위자 | ACT-001 (플레이어), ACT-003 (AI 봇) |
| 연결 REQ | REQ-005, FR-021, FR-022 |
| 전제 조건 | UC-002에서 "AI 봇 대전" + 난이도 + 위인 선택 완료 |
| 사후 조건 | 3판 2선승 경기가 끝나고 결과가 전적에 기록됨 (Elo 미반영 — spec-tablet Open Question #5) |

**정상 경로:**
1. 클라이언트가 `join`(토큰, heroId, 봇 난이도)을 보낸다
2. 서버가 GameRoom을 만들고 봇을 상대로 배치하며, 봇에게 위인 1명을 무작위 배정한다
3. 서버가 `matched`(상대: 봇 이름·난이도·heroId)와 `start`(seed, countdown)를 보낸다
4. 봇이 같은 시드의 블록을 난이도별 착지 판단 품질·조작 속도로 배치하고, 그 줄 삭제 정보가 사람과 같은 규칙으로 서버에서 공격 판정된다 (UC-008)
5. 말씀 대결이 열리면 봇이 난이도별 정답률·응답 시간으로 답하고 서버가 도착 순서로 판정한다 (UC-013)
6. 라운드·경기 종료는 UC-015와 같다

**대안 경로:**
- 4a. 쉬움 난이도 → 봇이 느리게 놓고 착지 실수가 잦다 / 어려움 → 빠르고 최적에 가까운 착지

**예외 경로:**
- E1. 플레이어 연결이 끊김 → 서버가 경기를 봇 승리로 종료하고 플레이어 패배를 전적에 기록 (UC-016과 같은 규칙)
- E2. 봇 처리 중 서버 오류 → 경기를 무효 처리하고 "경기를 계속할 수 없습니다" 메시지 후 로비로 이동 (전적 미기록)

| 전제 조건 | UC-002에서 "연습" + 위인 선택 완료 |

**정상 경로:**

**대안 경로:**

**예외 경로:**

### UC-015: 라운드·경기를 마치고 결과를 확인한다

| 항목 | 내용 |
|:---|:---|
| UC-ID | UC-015 |
| 유스케이스명 | 라운드·경기를 마치고 결과를 확인한다 |
| 행위자 | ACT-004 (GameRoom), ACT-001 (플레이어) |
| 연결 REQ | REQ-001, REQ-013, REQ-014, REQ-015, FR-007, FR-056, FR-062, FR-063, FR-065, FR-066, FR-067, FR-068, FR-070, NFR-006, C-003 |
| 전제 조건 | 대전 중 한 플레이어가 `topout`을 보냄 |
| 사후 조건 | 경기 결과가 저장되고(사람 대 사람이면 Elo 갱신), 결과 화면이 표시됨 |

**정상 경로:**
1. 플레이어 보드가 천장에 닿아 클라이언트가 `topout`을 보낸다
2. GameRoom이 상대를 라운드 승자로 판정하고 `roundEnd`(승패, 통계)를 보낸다
3. 시스템이 라운드 패배 쪽 보드를 회색으로 굳히며 무너뜨리고, 승리 쪽에 빛 연출을 보여 준다
4. 어느 쪽도 2승이 아니면 GameRoom이 새 시드로 다음 라운드 `start`를 보낸다
5. 한쪽이 2승하면 GameRoom이 `matchEnd`(승패, 통계)를 보낸다
6. 서버가 경기 결과(방 ID, 두 플레이어, 승자, 두 위인, 경기 시간, 통계)를 저장하고, 사람 대 사람이면 Elo로 두 레이팅을 갱신하며, 진행 기록(누적 판 수, 연속 패배 수, 직전 기록)과 업적을 갱신한다
7. 시스템이 결과 화면을 표시한다: 승리 시 빛 폭발 + 금빛 콘페티 + 승리 팡파르 + KJV 구절(예: 2 Timothy 4:7) / 패배 시 패배 효과음
8. 시스템이 그 경기의 대표 구절 말씀 카드, 개인 기록(최대 콤보, 분당 공격, 퀴즈 정답률), 이전 판 대비 성장 수치, 새로 달성한 업적, 레이팅 변화(사람 대 사람)를 보여 준다
9. 플레이어가 말씀 카드를 이미지로 저장하거나 공유한다
10. 플레이어가 "로비로"를 눌러 로비로 돌아간다

**대안 경로:**
- 6a. 연속 3판 진 플레이어 → 다음 판에 은혜 보정(받는 쓰레기 줄 −1, 게이지 충전 +15%) 적용, 화면에 "은혜" 아이콘만 표시 (FR-062)
- 6b. 다윗으로 한 경기 테트리스 5회 → 업적 "골리앗 사냥꾼" 달성 표시
- 9a. 브라우저가 기기 공유를 지원하지 않으면 → 이미지 저장만 제공

**예외 경로:**
- E1. 두 플레이어가 같은 서버 처리 단위에서 `topout` → 먼저 도착한 `topout`의 플레이어를 패배로 판정
- E2. 결과 저장 실패 → 결과 화면은 표시하고 "기록 저장에 실패했습니다" 안내, 서버 로그 기록
- E3. 이미지 저장·공유 실패 → "카드를 저장하지 못했습니다" 메시지

3. 시스템이 Vite 개발 서버와 `wrangler dev`(Workers + Durable Objects, 로컬 workerd 런타임, 로그인 불필요)를 함께 띄운다
4. Worker가 `.dev.vars`에 Supabase 키가 없음을 확인하고 DO 내장 SQLite 저장소로 동작한다
5. 클라이언트와 서버가 같은 `content/` JSON을 읽는다
6. 개발자가 브라우저 창 2개로 접속해 대전한다

**대안 경로:**
- 4a. `.dev.vars`에 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`가 있으면 → Supabase 어댑터로 자동 전환 (service role 키는 Worker에만 존재)

**예외 경로:**
- E1. 포트 충돌 → 실행 로그에 충돌 포트와 해결 방법 출력
- E2. Supabase 키가 있으나 연결 실패 → 서버 로그에 오류를 남기고 저장 요청은 실패 응답 (클라이언트는 UC-015 E2 처리)

5. 시스템이 통과·실패 결과를 출력한다

**대안 경로:**
- 4a. 브라우저가 설치되지 않음 → Playwright 브라우저 설치 명령 안내 후 재실행

**예외 경로:**
- E1. 테스트 실패 → 실패한 테스트명·기대값·실제값 출력, 종료 코드 1
- E2. 콘텐츠 검사 실패 → 출처 없는 항목 ID 목록 출력, 종료 코드 1
